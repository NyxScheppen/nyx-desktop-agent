# Nyx Agent 基本设计思路

> 本文合并产品设计与插件化 Harness 的基本思路，只表达目标、动机和取舍。
> **不作为任何系统事实、实现状态或验收标准的参考。** 当前系统先看 [facts 入口](../README.md#系统基本事实)，具体行为查代码。

## 持续存在的同伴

Nyx 的陪伴感应来自连续的经历和自主行为。她有自己的记忆、欲望、情绪、精力、活动和自我叙事；用户离开聊天窗口后，这些状态仍构成她的生活。

她知道自己是 AI，也想成为人类。角色表达借鉴 galgame，但目标是有连续状态的“同租者”，而非每轮重新开始的答题机器。项目同时是 Python 求职作品集，重视能解释、能观察和能验证的工程路径。

## 内在循环

外界经历影响内在状态，内在状态积累成欲望，欲望推动活动与表达，活动与表达留下记忆，记忆参与下一次判断与反思。

- **记忆**让关系和经历延续；原始经历应能被追溯，整理后的索引用来帮助想起它们。
- **欲望与活动**让主动行为有来源、有过程，也能在被打断后保留连续性。
- **内在生命**区分快速情绪反应与缓慢人格成长，避免普通闲聊立即改写身份。
- **表达与共读**把内在状态呈现为能被用户感受到的互动，而不是暴露工程参数。

这些是设计意图，不代表某一种算法、触发条件或具体数值。

## 单脑多感官，角色与引擎分离

同一角色可以通过桌面、浏览器、QQ 或其他实际需要的端点存在。不同端点应共享同一份经历，传输渠道不应各自复制一个互不相认的角色。

角色与传输是两个独立维度：角色定义身份及自己的状态，传输负责输入输出。切换一个端点上的角色，不应隐式控制其他端点。

从概念上分开角色内容、领域能力和通用运行底座：

- 角色卡承载身份、设定和初始倾向。
- 领域能力负责记忆、欲望、内在生命、活动、表达和阅读。
- Harness 承载装配、生命周期与执行支持；传输适配器连接外部存在面。

当前底座只服务 Nyx，保留在主项目内。只有出现真实复用需求时才考虑独立打包；跨进程协议、MCP 或 supervisor 也按实际消费者决定，不预留空接口。

## 可追溯与可恢复

自主行为需要回答“为什么发生、做到了哪里、失败后怎样继续”。设计上重视因果链、持久状态、明确的副作用边界，以及中断与重试时的连续性。

事件受理、某个系统处理完成、界面收到展示是不同阶段。数据库事务也不能撤销已经发生的模型请求、文件写入或外部消息；应在真实边界内承诺可靠性。

评估用于观察行为与成本，是否形成学习、以何种方式反馈，应由明确需求决定。流程验证与真实模型效果评测都需要，不能互相替代。

## 取舍

- 优先满足单用户陪伴，保持基础安全和数据最小化；本地或用户自选托管按实际使用选择。
- 界面呈现生活与互动，把调试细节放到需要它们的观察入口。
- 保持小而清楚的实现，避免为了设想中的未来建立框架。
- 文档解释操作、基本事实和设计动机；具体实现由代码承载，不维护另一套实现说明。
