# 本地发布质量门与按需框架化切片

> 本次任务的实施 spec，2026-11-06 用户已批准规划并要求实现。源码是系统事实来源；本文件限定本次工作和后续候选切片，不恢复旧规格书体系。

Q1—Q4 已完成，实施与当前运行结果见 [本地质量门验收记录](../eval/README.md#本地发布质量门2026-11-06)。框架化候选切片继续按下述启动条件另行审核。

## 目标与当前边界

- 接通现有 pytest → E2E 驱动 → Python 子进程的覆盖统计，保留发布检查的 90% 行覆盖率门槛。
- 复用已有路径验证，不为覆盖数字机械增加单元测试，不使用历史覆盖文件或排除生产代码抬高结果。
- 当前装配核心在 `nyx/harness.py`，只服务 Nyx；本次不拆包、不添加运行时接口，也不改变角色、事件或持久化行为。
- 框架化只记录实际需求触发的候选切片；没有独立消费者时保留当前应用内实现。

## 近期实施顺序

| 切片 | 最小工作 | 完成条件 |
|---|---|---|
| Q1 基线 | 使用已有 E2E 做子进程覆盖探针，隔离本次数据与旧数据 | 场景确实执行，但接入前其子进程路径未被统计；保存可比较证据 |
| Q2 统计接入 | 在现有 coverage 配置启用 subprocess patch，沿用 pytest-cov 合并 | 同一探针的真实执行行进入报告；失败及超时仍阻断检查 |
| Q3 有效缺口 | 根据合并后的缺失路径决定是否需要补充场景 | 全量 pytest 含全部成功 E2E，当前运行达到发布门槛；不根据历史数字宣称通过 |
| Q4 收口 | 静态检查、差异审查、操作说明与验收记录 | 本地命令可复现，未覆盖项明确，TODO 只保留未完成事项 |

优先使用锁定依赖已有的 coverage 子进程能力，不引入自制采集器或第二套测试入口。发布的 pytest 已包含统一 E2E 集合，独立 runner 作为定向诊断入口保留；两入口的驱动默认限时对齐，保留有限超时和失败传播。

## 影响路径与数据边界

- 写入口：pytest 主进程和 E2E 的 Python 子进程写入各自覆盖数据；pytest-cov 在会话结束合并并评估门槛。
- 消费者：coverage 报告、发布检查的退出码，以及本次验收记录；不进入业务数据库、事件流或前端。
- 生命周期：本次采集 → 子进程结束落盘 → 合并 → 报告。每轮使用干净数据，不 append 历史结果；子进程失败和统计通过是两个独立条件。
- 部分完成：失败场景仍使命令失败，部分覆盖数据不能证明场景完成。空驱动集合也不能视为 E2E 通过。
- 强杀与恢复：保留 P5 的真实 kill 场景。被强杀进程未保存的数据不保证可统计，不能为覆盖率修改崩溃语义。
- 并发与清理：采集文件按进程隔离；探针与全量运行的数据分开；验证产物放在临时目录，成功或失败结束后自动清理，仅保留必要结论。
- 无业务对象、schema、API 或运行时配置变更，领域状态迁移及删除不适用。

## 验证

1. 用同一个现有研究 E2E 做接入前后对照，核对行为通过及实际执行行，而非只检查配置文本。
2. 使用隔离探针确认失败子进程、超时和不足门槛均返回非零；探针及其输出在验证结束后自动清理。
3. 同步锁定开发依赖，运行 Ruff、Pyright 和带覆盖率的全量 pytest；隔离认证、数据库和真实外发配置。
4. 仅在真实缺失路径值得保护时补相关行为场景；不恢复测试文件索引或数量快照。
5. 检查新增文档链接、差异和敏感内容。未改前端、模型行为或冻结分发，不用历史页面/模型/制品结果替代本次证据。

修改范围：`pyproject.toml`、覆盖产物忽略项、`tests/test_e2e_acceptance.py`、`scripts/run_e2e.py`、`scripts/e2e/nyx-p5-conversation-e2e.py`、`docs/deployment.md`、`docs/eval/README.md`、`docs/TODO.md`、`docs/LessonsLearned.md` 及本文件。已有驱动只修正采集下的有限超时、空集合保护与后台任务启动就绪检查，超时保留已产生的诊断输出，不改变被验证的崩溃和恢复行为。

## 按需框架化后续

| 候选切片 | 启动条件与范围 | 验收边界 |
|---|---|---|
| F0 消费者确认 | 出现具名独立应用，明确最小用户路径、部署方式和需要复用的能力 | 证明现有应用内装配不足，选定必需的下一片并单独审核 |
| F1 事件与存储边界 | 消费者需要 durable event、重试与恢复 | 保持事务、FIFO、幂等、失败重放及 drain；业务表/迁移归 Nyx，涉及存储时验证 SQLite/PostgreSQL |
| F2 生命周期与调度 | 消费者需要复用启动、后台任务、监督和停止 | 验证半启动清理、取消、停止超时与重启；表达、欲望、反思等业务策略归 Nyx |
| F3 传输与投递 | 消费者确实需要第二应用复用传输，且已有必要的事件/存储边界 | 验证入向受理、outbox、游标、重连与关闭；保留至少一次语义和已知重复窗口 |
| F4 宿主与独立消费 | 具体消费者需要自己的组合根，前述必要能力已稳定 | 独立安装、启动与关闭，不反向依赖 Nyx；原应用角色隔离及端到端路径保持 |

以上不是固定抽包顺序或整体实施承诺，只取实际消费者需要的部分。MCP 由跨进程/远端工具需求触发，supervisor 编排由具体任务需求触发，不预置接口。

每片实施前核对全部写入口、消费者、状态变化，以及失败、部分完成、乱序、重放和删除路径；先审最小方案再改代码。涉及分发时再验证干净环境安装和冻结制品 smoke。
