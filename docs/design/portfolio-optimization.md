# 作品集成熟度优化

> 本文记录 Nyx Agent 作为求职作品集的工程化收尾路线，不定义产品领域契约。
> 产品行为仍以 `docs/specs/` 为准；CI/CD 的执行设计见 [`ci-cd.md`](ci-cd.md)。

## 基线与目标

基线更新于 2026-09-25。当前仓库已经具备完整桌面体验、六个业务 Facade、持久化事件总线、
REST/SSE 前端投影、严格类型检查和系统化测试。经本地验证：

- 后端 `ruff` 与严格 `pyright` 通过，`1060 passed, 1 skipped`；
- 后端语句覆盖率为 91.71%；
- 前端 `23` 个测试文件、`305 passed`，生产构建通过；
- Tauri `cargo check --locked` 通过，Windows MSI/NSIS 能生成；
- 架构、领域契约、源码事实和失败经验已有分层文档。

因此主要差距已经不是继续增加业务功能，而是让第三方能够**验证、复现、安装并理解**现有成果。
阶段目标是把项目从“强工程实现”推进到“可重复交付的成熟作品集”，不把它包装成已经经过大规模
用户验证的商业产品。

## 优化原则

1. **证据优先于宣称**：README 中的测试、构建和发布结论必须由自动化结果支撑。
2. **复用优先于重写**：CI/CD 调用本地已经使用的命令和构建入口，不维护第二套脚本语义。
3. **交付优先于扩功能**：完成首个可信 release 前，电脑控制和新的业务模块不进入主线。
4. **真实制品优先于开发态**：发布验收必须覆盖冻结 sidecar、桌面壳和安装包，而不只验证源码测试。
5. **诚实标注边界**：未签名、未经真实用户长期验证和暂不支持的平台都要明确写出。

## 优先级路线

### P0：仓库事实可信

- [x] 修正 README 中 Facade 数量、测试数量和占位徽章等过期信息。
- [x] 增加可提交的 `.env.example`，并让 `.gitignore` 对它显式放行。
- [ ] 决定并补充开源许可证；在决定前不把仓库描述为可自由再分发。
- [x] 用真实 CI 状态徽章替代手写“全绿”结论。

**完成标准**：新读者只读 README 就能得到与当前源码、测试和发布状态一致的信息。

### P1：持续集成

- [x] 为 Python 质量工具建立可复现的开发依赖入口和锁定文件。
- [x] PR 自动执行后端 lint、类型检查、测试与覆盖率门槛。
- [x] PR 自动执行前端测试、TypeScript/Vite 构建和 Rust `cargo check --locked`。
- [ ] 将上述检查设为 `main` 分支合并前的 required checks。

**完成标准**：任意干净 clone 都能按锁定依赖重跑质量门；PR 不能绕过失败检查进入 `main`。

### P2：持续交付

- [x] `main` 和手动触发构建 Windows x64 sidecar 与 Tauri 安装包。
- [x] 对真实冻结制品执行 REST/SSE、启动就绪和退出回收 smoke。
- [x] `vX.Y.Z` 标签校验所有版本源一致后生成安装包和 SHA256 校验文件。
- [x] 标签构建先生成 GitHub draft release；签名方案确认后再考虑自动公开发布。
- [x] 为失败构建上传 `backend.log` 和必要诊断产物，不上传用户数据或密钥。

**完成标准**：发布页中的二进制来自同一标签的自动构建，且通过真实制品 smoke，不依赖开发机文件。

流水线实现与本地制品验证已完成；此完成标准仍需首次 `vX.Y.Z` 线上 tag 预演取得 GitHub 侧证据。

### P3：作品集表达

- [ ] 更新演示素材，覆盖桌宠、慢通道对话、共读、活动恢复和事件溯源，而非只展示单个页面。
- [ ] 从 `docs/LessonsLearned.md` 选取至少三个案例，整理为“故障—根因—修复—回归测试”。
- [ ] 在 README 中提供 5 分钟阅读路径：产品价值、架构图、可靠性案例、运行方法、发布包。
- [ ] 为首个 release 编写面向招聘者和试用者的已知限制，而不是只列 commit。

**完成标准**：不了解项目的人能在 5 分钟内说清它解决什么问题、技术难点在哪里、证据是什么。

### P4：真实使用证据

- [ ] 邀请 3 至 5 名外部试用者连续使用至少两周。
- [ ] 将安装失败、启动失败、数据恢复和交互困惑转成可复现 issue。
- [ ] 发布至少一个基于真实反馈的修复版本，并在 release notes 中关联问题与回归测试。

**完成标准**：项目不再只有作者环境中的成功记录，至少形成一次“外部反馈—修复—再发布”闭环。

## 暂不优先

- 不为作品集评分继续堆叠 computer-use、更多模型提供商或新的业务 Facade。
- Windows 发布链稳定前，不同时承诺 macOS/Linux 安装包。
- 不为桌面单用户应用引入 Kubernetes、远程部署平台或微服务拆分。
- 不把测试数量当作唯一指标；后续测试增量优先覆盖发布制品和用户路径。

## 成熟作品集完成定义

- README、设计文档、源码与自动化结果不存在已知事实冲突；
- PR 质量门、`main` 制品构建和标签交付三条路径均可重复执行；
- 发布制品有版本、校验和、已知限制及 smoke 证据；
- 无真实 API Key 的 CI 环境也能完成全部测试和非 LLM smoke；
- 至少三个关键工程决策能够从问题记录追到实现和回归测试；
- 至少有一个外部试用反馈驱动的修复 release。
