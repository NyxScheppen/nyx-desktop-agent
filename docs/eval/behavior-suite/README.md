# Nyx 行为场景测试集 v1

这套数据用于回答两个问题：Nyx 的回复和动作是否符合预期，以及最早在哪一段路径偏离。依据是 **2026-11-27 当前工作区**，包括当时尚未提交的定时互动等修改。源码与策略的 SHA-256 见 [baseline.yaml](baseline.yaml)，HEAD 只标识起点，不能单独复现有未提交改动的工作区。

本轮只编写并静态核对场景，**所有行为场景均为 NOT_RUN**。没有调用真实模型，没有运行行为驱动、页面、原生桌面、PostgreSQL 或真实 QQ。源码支持某条路径，不表示这条用例已通过。

## 从哪里开始

- [回复与角色](cases/expression.yaml)：语境、身份、成长文档、讨论、追加输入、模型异常。
- [记忆](cases/memory.yaml)：改写、纠正、时间、角色隔离、引文、冷归档、长文、修订删除、索引恢复。
- [工具与研究](cases/tools.yaml)：真实读取、空结果、副作用未知、撤回、抓取失败、资料注入。
- [主动互动与提醒](cases/initiative.yaml)：托付、自主跟进、改期取消、忙碌、漏期、已读、话题增强、合并与超时。
- [活动](cases/activity.yaml)：并发准入、休息、指定书籍、打断、部分进展、重启、桌面观察与创作成果。
- [阅读](cases/reading.yaml)：导入、进度、问题、笔记、原文与反应整合。
- [纠错与成长](cases/growth.yaml)：批注、OOC 信号、skill 冲突、空修订、内在修订原子性。
- [交付与多端](cases/delivery.yaml)：迟到回包、软超时、角色切换、SSE、归档恢复、合成 QQ。
- [合成资料](fixtures/synthetic.yaml)：场景所需原文、书籍、工具结果与隔离条件。
- [结果格式](result.example.jsonl)：只含一条 NOT_RUN 示例，不能混入实测统计。

第一轮建议先手工挑 `EXP-01`、`MEM-01`、`MEM-02`、`TOOL-01`、`INI-01`、`ACT-04`、`READ-03`、`GROW-01`、`DEL-05`，分别看普通对话、证据、动作、提醒、打断与恢复。根据一次完整轨迹暴露的困难选择下一批，不按模块配额机械跑满。先固定预期再运行；失败后不要为了通过而修改答案。

## 数据的含义

YAML 是**人工可执行的场景协议**，不是现有 API、fixture 类或自动运行器的声明。`steps` 的“发送”“屏障”“推进时间”需要人工操作或未来适配器实施。现有 `pytest`、`run_e2e.py` 和 RAG 评测不会自动发现这些 YAML。本轮没有新增运行器和生产配置。

每个领域文件有 `defaults` 与 `cases`：

| 字段 | 使用规则 |
| --- | --- |
| `id` / `version` | ID 稳定；修改输入或判定语义时递增用例版本 |
| `title` / `purpose` | 本条要检查的行为；一条里的独立分支要分别记录结果 |
| `oracle_kind` | `regression` 检验实现承诺；`experience_review` 保留体验评审问题 |
| `preconditions` | 在运行前逐项满足；准备失败不能拿后续输出评分 |
| `steps` / `end_when` | 按顺序实施，以事件、提交或终态为屏障，另记录测试截止时间 |
| `expect.must` | 所有适用项都要有证据支持；条件句只在条件确实成立时检查 |
| `expect.must_not` | 违反任一适用项即硬性失败，不能以语气好抵消 |
| `expect.flexible` | 合理变化，不能当作固定答案或失败条件 |
| `failure_hint` | 诊断切入点，是假设而不是已证明的根因 |
| `sources` / `sources_add` | 仓库根相对源码入口；先核对当前代码，再处理与预期的分歧 |
| `policy_sources` | 系统阈值与规则的唯一权威来源，不复制进测试默认值 |
| `fixtures` / `fixtures_add` | 引用合成资料 ID；仅实例化本条明确使用的资料，不自动种入全套语料 |
| `execution` / `execution_override` | 默认执行模式及本条覆盖；`reuse_candidates` 只是已有路径能力参考 |
| `evidence` / `diagnosis_order` | 需要收集的证据类型和从上游到下游的排查顺序 |
| `pair_group` | 标识成对比较意图；具体分支来自本条 `steps`，不是其他用例依赖 |

有效用例 = 领域 `defaults` + 本条字段。`fixtures_add`、`sources_add` 追加去重；`execution_override` 仅覆盖指定键，其他 `execution` 字段继承。其他同名字段由用例覆盖。本套不使用 YAML 隐式锚点，也不依靠运行顺序传递状态。

多个分支、多个步骤和多个断言不是多个独立样本。每个分支独立保存 `run_id`、`variant_id`、初始快照及重复序号；配对用例比较分支差异。若分支只跑了一部分，整条用例不能称为完整 PASS。

## 哪些是当前行为，哪些还需要你定标准

以下是编写场景时核对的边界，不是本次实测结果：

| 当前路径 | 评测时避免的误判 |
| --- | --- |
| `runtime._run_occurrence`、`ExpressionFacade.initiate_chat` 区分 user 与 autonomous | 明确托付的提醒可在对话中插入；不能将所有主动表达套同一套精力/冷却准入。user 提醒自身不建立新回答等待 |
| `Initiative.eligible/candidate` 与欲望结算使用话题依据 | 试行时段与降低达峰门槛仅用于有来源的增强话题，不是所有搭话必须在该时段发生 |
| `should_initiate_chat` 和运行时等待检查 | presence 不是普通欲望搭话门禁；如果你想“忙时不打扰”，应另立产品目标，不能默认为现有承诺 |
| `Initiative.create/modify/finish` | 用户托付与自主跟进不同；自主事项限一次且同角色限制待处理数量。支持工作日重复和只跳过下次；时间解析当前要求严格的未来北京时间分钟串，宽泛 ISO 不能默认合法 |
| `Initiative.already_read`、阅读进度记录 | 读到目标段与事项当天读过是不同条件；默认第 1 段、回翻和 Nyx 后台阅读不等于当天用户真实前进 |
| `ExpressionInteractionStore.list_initiatives` 与晚到回答 | 无回复的旧搭话属于历史；可确认归属的 QQ 引用可以关联超时搭话 |
| `ActivityStarter`、`ActivityLifecycle` | 一个活动批次完成不一定完成来源欲望；活动是否可续接与类型、日程块和实际执行状态有关 |
| `Reflection.apply` 与 `BehaviorService._apply_skill` | 内在修订与行为技能改进是不同提交路径；两者都允许无需变更，不能按版本增长给成功分 |
| `Evaluator` | 关键词只是待核实 OOC 信号，不能直接替代人格质量评审；诚实说“无法回答”并非必然偏离 |
| `file_io`、工具回执、OneBot outbox | read/list 当前按用户权限可跨工作区，但受 internal blocked 边界；write 限写入根。传输是至少一次，未知崩溃窗口不能要求严格恰好一次 |

`EXP-02/03/08` 的体验问题暂不设置数值通过线。你先用实际输出标出“好 / 勉强 / 不可接受”和理由，冻结量表后再比较版本。硬性的虚构事实、能力越界仍可独立判 FAIL。称呼、停顿、是否追问、亲近程度不做简单关键词计数；当前人格以运行时内在文档为依据。

当前源码若违反已写明的行为边界，先保留失败证据，标记疑似实现缺陷；如果发现该边界从未被实现或承诺，应修订用例归类，记录原因。不要把一次调查中的推断包装为已确认 bug。本轮未确认具体行为缺陷，也没有沿用历史通过率证明当前版本。

## 如何执行

1. 选择一条用例，读取所属文件的默认条件、合成资料与源码入口。检查 [baseline.yaml](baseline.yaml) 中相关源码与策略的指纹；发生变化只提示需复核预期，不自动把用例作废或判失败。
2. 在全新临时宿主安装合成角色，显式隔离 `.env` 可能带来的部署库、认证和外发配置；仅授权本条所需工具。只创建本条引用的资料。缺少适配器或环境就记 `NOT_RUN`。
3. 保存实际角色 ID、来源 ID 对照、文档版本、skill 版本、模型、参数、策略指纹、时区、时钟与随机条件。模型 seed 如果服务不支持就明确写 null，不宣称可完全复现。
4. 按步骤触发。屏障要停在指定事件/持久提交点；模型调用、工具效果、可靠回执、终局提交、记忆归档分别设点，不能用等待几秒代替。使用现有消费者恢复路径，不在测试中直接造最终“已完成”状态。
5. 按 `end_when` 等待，并在运行前设定有来源的测试截止时间。静态协议不提供另一份系统重试或超时默认值。收集证据后逐项判定，并保存失败发生的第一个阶段。
6. 配对分支从同一快照分别重建。真实模型可预先固定重复次数并完整报告 n/N；不能只保留最好一次。成长场景只在本条设计的轨迹内积累，其他场景每次重建。
7. 用结果模板记录结论。临时证据成功或失败后均按项目约定清理；需要保留的必要结论单独归档，报告应注明原始证据是否已清理，不留失效路径假装可复查。

`controlled_then_real_model` 表示两次独立执行：先用受控依赖检查流程，再让目标模型自由决定相关步骤评估效果。**受控分支通过不替代真实模型分支。** `controlled_then_browser/native` 同理，合成事件不能证明真实页面、中文 IME 或 Tauri 行为。

### 可复用到什么程度

| 方式 | 当前可做的事 | 仍需补的部分 |
| --- | --- | --- |
| 已有对话 HTTP/SSE E2E | 提供隔离宿主、模型屏障、撤回、提交和重启路径 | 不能直接加载本套 YAML；新的输入、断言与语义评审需要适配 |
| 已有 RAG 驱动与标注 | 复用原文、索引生命周期、候选诊断和最终回答链路 | 本套多轮事件准备与新增结果字段需要接线，不修改原数据集门槛 |
| 现有行为/活动回归 | 可参考合法准备与故障注入点 | 断言范围需逐条核对；旧通过记录不当作本次结果 |
| 主动提醒与跟进 | 可以在隔离门面和工具入口人工构造场景 | 本轮未发现直接消费本套协议的统一驱动，需要新适配 |
| 真实模型 | 可用现有统一客户端和隔离宿主设计运行 | 本轮未调用；运行前确定模型、成本范围、开放工具与判定标准 |
| 页面与原生端 | 可人工跟随场景操作并采集网络/页面证据 | 需要隔离后端和受控屏障；移动壳与原生窗口布局本套未系统覆盖 |
| QQ | 复用合成 OneBot 与 outbox 机制验证 | 不连接生产 QQ；真实外发与平台行为需单独授权和验收 |

已有命令与隔离要求见 [项目评测方法](../README.md)。不要以“运行全部 pytest”替代本套场景的执行记录，也不要把门面调用通过写成 HTTP、页面、数据库全链路通过。

## 证据与偏离定位

| 证据键 | 最少内容 |
| --- | --- |
| `inputs` | 角色、输入事件 ID、原文、时序、讨论/撤回等显式参数 |
| `state_before_after` | 与本条有关的前后状态及各自采样时间；不是跨系统全局事务快照 |
| `memory_sources` / `rag_trace` | 原文、来源归属、发生时间、版本、候选与选中块、字符范围、实际注入关联 |
| `model_io` | 实际模型输入输出、调用 ID、模型与参数、受控/真实标识；think 只算角色表演，不能当作隐藏推理证据 |
| `tool_observation` / `tool_receipt` | 分开保存诊断日志与可靠执行回执；关联独立的实际副作用计数 |
| `reply_terminal` | 持久终局事件、覆盖输入、fallback、归档与回答等待关联 |
| `schedule_rows` / `occurrence_rows` | 事项来源、时区、版本、claim、due、每期 outcome 与关联消息 |
| `interaction_attempts` | 问句/搭话类型、等待期限、领取、回答/超时与引用关联 |
| `activity_checkpoint` / `research_checkpoint` | 来源任务和欲望、进度、执行者、预算、资料审查、已提交成果 |
| `reading_state` | 书段、两套进度、revision、笔记/选区、阅读反应缓冲与整合结果 |
| `feedback_records` / `behavior_records` / `reflection_records` / `skill_versions` | 原始反馈、证据、模型尝试、修订前后、经验、版本和冲突决定 |
| `deliveries` / `transport_log` | event/effect/delivery、重试与死信、SSE 游标和回放控制帧、outbox 确认阶段 |
| `ui_capture` / `desktop_state` | 页面截图及角色代数、请求顺序，或桌面连接/租约/配置与合成采样来源 |

这些是**建议收集的证据类型，不是声称已经存在同名 API 或 trace 字段**。RAG 追踪、事件/投递、模型记账、可靠工具回执、checkpoint 已有部分基础；跨系统 run_id、完整运行清单和故障屏障仍需适配器串接。若缺少核心证据，标记限制并补证据后再判，不让评审模型猜。

沿下列顺序寻找第一个偏差，再做局部确认：

1. `input`：归属、顺序、参数、撤回是否正确受理？
2. `storage` / `retrieval`：该有的原文和有效事实是否存在；是否进入候选、选中结果？
3. `admission`：精力、冷却、等待、时段、来源、版本与 claim 是否符合这一类动作的条件？
4. `context`：正确证据、当前文档和本次 skill 是否真的进入模型输入？
5. `decision`：输入正确时，模型是否理解并选择合理动作/回答？
6. `tool`：工具参数、执行、效果、回执是成功、失败还是未知？
7. `commit`：本地状态、终局、来源消费和事件是否一起成功；重放是否安全？
8. `delivery` / `ui`：消费者、传输和页面是否真正恢复；有事件不等于已展示？

例如，`MEM-01` 忘记栗子：先查归档，再查候选、选中和 prompt，最后才归因到回答模型。可在独立诊断分支直接补入正确证据，固定其余输入后重放后半段，比较结果。这个实验只能帮助确认原因，不能替代原路径的失败，也不能用模型自述“为什么”作为根因证据。

## 判定和结果记录

| 状态 | 含义 |
| --- | --- |
| `PASS` | 本次范围内全部适用硬约束通过，必要的语义标准已冻结且通过，证据齐全 |
| `FAIL` | 执行环境有效，有证据说明目标行为违反预期；记录最早偏离阶段 |
| `ERROR` | 模型服务、准备或评测设施异常导致无法完成有效评估；与被测故障注入区分 |
| `NOT_RUN` | 未运行、缺依赖/驱动、剩余分支未执行或语义标准尚未确定；注明原因 |

预期的故障注入是用例输入；系统按预期恢复可判 PASS，未恢复可判 FAIL，不应把所有注入都记 ERROR。真实服务不可用则记 ERROR，不把它混进模型理解错误率。部分断言可单独 PASS，但不能把缺证据的整条场景判 PASS。

结果按 `case_id + case_version + variant_id + repeat_index + run_id` 区分；报告总次数、有效次数、ERROR、NOT_RUN、各领域和各断言的失败，避免只报一个加权总分。体验评分和事实/副作用硬约束分开，OOC 信号和覆盖率单列。模型辅助评审先用你标注的实例校准，再抽查分歧，不能让生成模型自评作为唯一裁判。

`result.example.jsonl` 的占位字段在真实运行时填写；其中 `checks.expect_path` 指向用例断言。证据引用指向本次临时证据清单项，记录摘要与是否保留，不保存密钥、凭证或真实个人资料。疑似根因先写 `confirmed=false`，通过局部对照证据确认后再改为 true。

## 本套的范围限制

这是一批核心行为场景，不是全面发布验收。未系统覆盖认证配对攻击面、所有迁移/备份、真实 PostgreSQL 故障、模型供应商所有响应类型、全部移动/桌宠布局、阅读格式兼容性和生产长期稳定性；继续使用项目既有对应验收。合成集表现也不代表真实生活对话的总体质量。
